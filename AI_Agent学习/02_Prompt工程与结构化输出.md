# 专题-02 - Prompt 工程与结构化输出

## 🎯 学习目标
- 理解 Prompt 是与模型交互的**唯一接口**，写 Prompt 是一门工程而非玄学
- 掌握 Prompt 的五个零件：角色、指令、上下文、示例、输出格式
- 理解 few-shot 为什么有效（联系你学过的 Transformer 原理）
- 掌握结构化输出三板斧：格式约定、JSON mode、Schema 约束，以及解析失败的兜底

---

## 📚 核心知识点

### 1. 为什么 Prompt 是"工程"

你在训练课程里学过：模型参数训练完就冻住了，使用时**唯一可调的就是输入文本**。同一个模型，Prompt 写得好与差，效果可以差出几个档次——而且 Prompt 可以版本管理、可以 A/B 测试、可以写单测。把它当代码对待，就是"工程"；把它当许愿，就是"玄学"。

对 Agent 来说 Prompt 更关键：**Agent 的每一步决策都靠 Prompt 驱动**，Prompt 里写错了工具的用法，模型就会一直错下去——没有任何梯度来纠正它。

### 2. Prompt 解剖：五个零件

![Prompt 解剖](assets/prompt_anatomy.png)

**① 角色设定（system prompt）**：定身份、语气、边界。"你是资深数据分析师"不只是客套——它会显著改变模型选择词汇和推理深度的倾向。Agent 的 system prompt 通常还要写：你有哪些工具、什么情况下该用、什么情况下拒绝。

**② 任务指令（instruction）**：一句话说清要什么，**动词开头**。"总结"/"分类"/"提取"/"判断"比"帮我看看这段文字"有效得多。

**③ 上下文（context）**：背景资料。RAG（专题-04）检索回来的内容、对话历史都放在这里。原则：**模型不知道的、答对必需的，才放**——塞得越多越贵，干扰还越大。

**④ 示例（few-shot）**：给 1~3 个"输入 → 输出"样例，模型照猫画虎。这是稳定输出格式**最便宜**的手段。

**⑤ 输出格式（format）**：Agent 的生命线。模型的输出要被程序解析，格式必须像合同一样精确。

### 3. Few-shot 为什么有效？——用你学过的原理解释

你在 Transformer 专题学过：推理时没有梯度、参数不变。那给几个示例，模型怎么就"学会"了格式？

答案藏在自注意力里：示例作为**上文**进入序列，后面每个位置的注意力都能"看到"这些示例（Q 去匹配示例中的 K，取回示例的 V 里的模式）。模型在预训练时见过海量"按样例模仿"的文本模式，所以示例一摆，它就知道该续写什么格式。这叫 **in-context learning（上下文学习）**——学习发生在前向传播里，不碰参数。

推论：示例选得好不好，直接决定模仿质量。三个挑选原则：**覆盖典型情况、格式完全一致、放在靠近问题的地方**。

### 4. 结构化输出：Agent 的生命线

Agent 的程序要从模型输出里提取"调哪个工具、参数什么"。模型天生说自然语言，怎么让它稳定输出机器可解析的结果？三板斧，可靠性递增：

**板斧一：Prompt 里约定格式（最弱）**

```
请严格用以下 JSON 格式回答，不要输出任何其他文字：
{"action": "工具名", "args": {"参数名": "值"}}
```
配 few-shot 示例效果更好。缺点：模型偶尔还是会多嘴（"好的，以下是 JSON：……"），解析就崩。

**板斧二：JSON mode（中等）**

API 层面的开关（`response_format={"type": "json_object"}`），强制输出是合法 JSON。保证可解析，但**字段结构仍可能不符合你的预期**。

**板斧三：Schema 约束 / Function Calling（最强）**

把期望的结构写成 JSON Schema 交给 API，模型被约束必须按 Schema 填：

```json
{
  "name": "search",
  "description": "搜索互联网获取实时信息",
  "parameters": {
    "type": "object",
    "properties": {"q": {"type": "string", "description": "搜索关键词"}},
    "required": ["q"]
  }
}
```

这是专题-03 工具调用的正式机制。**工程原则：能用 Schema 就不用裸 Prompt 约定。**

### 5. 解析失败怎么办：校验 + 重试

就算用了最强的板斧，也要假设输出会坏。标准兜底模式：

```python
for attempt in range(3):                    # 最多重试 3 次
    raw = call_llm(prompt)
    try:
        data = json.loads(raw)              # 第一步：能解析吗
        validate(data, schema)              # 第二步：结构对吗（Pydantic/jsonschema）
        break                               # 通过，放行
    except (json.JSONDecodeError, ValidationError) as e:
        prompt += f"\n上次输出有误：{e}，请修正"   # 把错误喂回去让它改
else:
    raise AgentError("模型连续 3 次输出非法，放弃")  # 兜底失败，向上报错
```

两个要点：**错误信息喂回去**（模型看到自己的错通常能修对）、**重试必须有上限**（01 篇说的"刹车"）。

### 6. 实用技巧速查

| 技巧 | 做法 | 场景 |
|---|---|---|
| 思维链 CoT | "让我们一步步思考" | 数学/推理题，准确率明显提升 |
| 分隔符 | 用 ``` 或 <<< >>> 包裹资料 | 防止资料里的文字被当成指令 |
| 负面指令 | "不要编造、不知道就说不知道" | 抑制幻觉（配合 RAG） |
| 长度控制 | "用 3 句话以内" | 避免啰嗦，省 token |
| 先输出再解释 | 要求 JSON 在前、解释在后（或禁止解释） | 方便解析 |

### 7. 一句对照：许愿，和一份能解析的合同

坏的写法把格式当成客气话：

```text
帮我看看特斯拉营收，谢谢！最好用 json 哦。
```

模型会先说「好的」，再夹一段 JSON。`json.loads` 在第一个汉字上就失败。`practice/agent01_json_output.py` 的单个坏例子就是这句「好的，以下是 JSON」。

能交给程序的写法把字段写死：

```text
你是检索助理。只输出一个 JSON 对象，不要前言，不要 Markdown。
字段：action，只能是 search 或 finish；args.q，字符串。
不知道就用 finish，不要编造数字。
示例：{"action":"search","args":{"q":"Tesla revenue"}}
```

示例里的引号、字段名必须和你的 `validate` 一模一样。差一个键，模型会照着错的模仿。

## 🔬 原理

### 你改的是条件分布，不是在对程序下命令

模型没有「指令寄存器」。一次生成是在算

\[
p(y_1, y_2, \ldots, y_T \mid x) = \prod_{t=1}^{T} p(y_t \mid x, y_{<t})
\]

\(x\) 就是你这次送进去的全部 token：角色、资料、示例、用户的话。改 Prompt，就是改 \(x\)，从而改每一个下一步的分布。模型不会另找一个通道去「服从」你。它只是在这个条件下，某些续写的概率变高了。

这也是客套话帮助不大的原因。「请」「谢谢」这些 token 和「下一个字符应该是 `{`」的关系很弱，占掉的位置却要参与后面的注意力。真正搬动概率质量的，是字段名、示例、以及「不要前言」这种和非法续写直接矛盾的约束。

### Few-shot 为什么主要稳定格式，却教不会新算法

前文已经说：示例进了序列，后面的位置能注意到它们。再往下看一层机制。

预训练文本里有大量「前面一个样子，后面跟着同一种样子」的片段。推理时，一种被研究得比较清楚的注意力行为是：当前前缀去前文里找相似的前缀，把当时紧跟着的那种续写模式抄过来。格式模仿（看到三个 JSON 示例，第四个也以 `{` 开头）主要靠这个。

它有一条边界：示例里没有的计算，抄写不会凭空出现。你给三个错误的同比公式，模型会稳定地模仿错误公式。Few-shot 放大的是示例里已经展示的映射，不是模型参数里没有的算法。复杂推理还是靠预训练里已经形成的那些计算，示例只是把输出拽到你要的格式上。

所以挑选示例的原则有机制含义：**格式必须一致**（否则要抄的模式互相打架），**放在靠近问题的位置**（中间的 token 更容易被弱化，见 04、08 篇），**覆盖你真正会遇到的分支**（没展示过的分支，概率仍然落在模型自己的习惯上）。

### 三板斧的差别，是分布有没有被截断

| 做法 | 生成时的分布 |
|---|---|
| 只在 Prompt 里约定格式 | 仍然是原来的 \(p(y_t\mid\ldots)\)。`{` 的概率也许最高，但「好的」的概率没有被设成 0 |
| JSON mode | 解码时把不能构成合法 JSON 的 token 掩掉，再在剩下的里面采样。非法字符串的概率变成 0。字段语义不管 |
| Schema / 约束解码 | 掩码更紧：下一个 token 还必须符合那张 Schema 走到目前这一步所允许的字符。名字不在枚举里、缺必填字段，在解码阶段就走不出去 |

Prompt 约定是在希望峰值刚好落在合法字符串上。约束解码是在改变采样的支撑集：不合法的续写不再参与 softmax。这就是「能用 Schema 就不用裸约定」的原理，不是口味。

温度 \(T\) 把 logits 变成 \(z/T\) 再 softmax。\(T\) 变大，分布变平，峰值和次峰的差距变小，格式更容易漂。工具调用要的是峰值，不是多样性，所以 Agent 循环里温度通常取得低。需要多种写法的创作步骤才把温度调高，并且不要和「必须可解析」放在同一步。

### 错误喂回去，是在改条件，所以分布会动

练习里不喂错误时，三次看到的是同一份坏输出。原理就是上一行公式：\(x\) 没变，\(p(y\mid x)\) 就不变，再采样还是同一类续写。

把报错写进 \(x\) 之后，条件变了，「再输出一次那个缺括号的字符串」的概率下降，「输出能通过刚才那条报错的字符串」的概率上升。这不是模型在反省性格，是新 token 改变了条件分布。报错写得越像「哪一个约束被破坏了」，概率越往修好的那个字符串上搬。只写「不对，重来」提供的特征太少，分布几乎不动。

重试必须有上限，因为新条件也不保证峰值落在合法集里。连续几次之后再采样，期望的成功率增益会变小，花费照旧。

## ⚠️ 常见坑

1. Prompt 里堆礼貌用语——模型不需要"请""谢谢"，简洁明确的指令更有效
2. 用自然语言描述格式却不给示例——模型对格式的理解和你的预期十有八九不一致
3. 解析裸文本不做校验——上线第一天就会被一句"好的！"打崩
4. 重试不带上次错误——同样的错模型会原样再犯
5. 上下文贪多——无关资料会稀释注意力，又贵又容易带偏

## 📝 小结

- Prompt 五零件：角色、指令、上下文、示例、格式——Agent 场景里"格式"最重要
- Few-shot 的原理：示例进上下文，自注意力照猫画虎，不碰参数
- 结构化输出三板斧：格式约定 < JSON mode < Schema 约束，能用 Schema 不用裸约定
- 解析必须配「校验 + 错误喂回 + 有上限的重试」
- 下一步：专题-03，把结构化输出用在正道上——让模型决定调用哪个工具，手写 ReAct 循环

## 💬 自学问答

**问：JSON mode 打开了，为什么还要 validate？**
JSON mode 只保证括号配对、能被 `json.loads`。字段可以完全不是你要的。`{"foo": 1}` 就是合法 JSON。

**问：重试三次都失败，该把原始输出显示给用户吗？**
不要。向用户说「这次没有得到可解析的结果」，把原始输出留在日志里。原始输出可能夹着模型瞎编的内容。

**问：示例是不是越多越好？**
01 到 03 个、格式完全一致，就够。十个互相矛盾的示例会让格式更飘，也更贵。

## 📝 小测验

1. 模型回了「好的：」加一段正确 JSON。这算 JSON mode 能解决的问题，还是 Schema 能解决的问题，还是两个都不管、要靠你解析时拒绝？
2. 为什么重试时要把上一次的报错写回去？
3. Key 应该放在哪？
4. JSON mode 已经打开时，模型还有可能输出 `{"foo": 1}` 吗？为什么？

### 参考答案

1. 这是「输出里夹了人话」。JSON mode 会从 API 层就禁止这种输出。你自己解析时也应该拒绝，不能从长文里随便抠第一段花括号——花括号可能出现在说明文字里。
2. 不写回去，条件 \(x\) 没变，下一步的分布就不变。练习里不喂错误时，三次就是同一份坏输出。
3. 放在环境变量里。不写进代码，不写进笔记仓库，不写进 Prompt。
4. 有可能。JSON mode 把「不是合法 JSON」的续写概率设成 0，不约束有哪些键。`{"foo": 1}` 是合法 JSON。键的约束要靠 Schema，或者靠你自己的 validate。
